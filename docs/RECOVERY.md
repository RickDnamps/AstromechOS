# Recovery procedures — AstromechOS

> Resolved-failure playbook. Each entry is a symptom → diagnostic → root cause →
> fix (with the locking commit) for a bug that has already been fixed in the
> tree. Kept out of `CLAUDE.md` to keep the always-on context lean; pointed to
> from `CLAUDE.md` § Recovery. Most entries also have a `bd memories <slug>`
> with the deep detail.

---

**`sounds_index.json` corrompu** : AudioDriver.setup() retourne False, aucun handler `S:`, /audio/play renvoie 200 mais silence total. Diagnostic + fix : `bd memories audio-sounds-index-corruption` + `scripts/fix_slave_sounds_index.py`.

**UI element "ne marche que sur click" (ex: STATUS pill reste verte sauf si on click)** : symptôme d'un `TypeError` mid-`StatusPoller._pollOnce()`. La ligne qui throw halt l'exécution → toutes les updates UI suivantes (cockpit pill, mode pills, lockMgr sync) ne tournent JAMAIS. Le click trigger un fresh path qui bypass le `_pollOnce` cassé. Diagnostic : DevTools Console après reload → cherche `TypeError: X is not a function at _pollOnce`. Fix : `typeof X.method === 'function'` guard ou try/catch autour de la section concernée. Voir `feedback_status_poller_resilience.md` memory.

**Cache navigateur stale après deploy** : asset URLs dans `templates/index.html` utilisent `?v={{ version }}` (flask passe `_read_version()` à `render_template`). Sans ce query string, le service worker `astromech-<commit>` cache ne s'active qu'à la 2ème navigation après deploy → opérateur voit "le fix n'a pas pris" alors que c'est du cache. Voir `project_cache_bust_pattern.md`.

**`astromech-master.service: Failed with result 'exit-code'` à CHAQUE restart (≠ crash opérationnel)** : le handler SIGTERM (`main.py::shutdown`) lève une exception AVANT `sys.exit(0)` → exit 1 → systemd "Failed", ET tout le cleanup après la ligne qui plante est sauté (UART/servos/BT jamais relâchés). Pas un crash en marche — chaque "Failed" est collé à un `Stopping` (= un deploy/restart). Diagnostic : `journalctl -u astromech-master` autour du "Stopping" → traceback entre "Shutdown signal received" et "status=1". Cause historique (fix `31c034e`) : `deploy.stop()` appelé alors que `DeployController` n'a pas de `stop()`. **Règle** : chaque étape de `shutdown()` DOIT être guardée (`_safe()` try/except) → un composant défaillant n'avorte jamais les autres et le process atteint TOUJOURS `sys.exit(0)`. Arrêt sain = "Master shut down cleanly" + systemd "Deactivated successfully". Détails : `bd memories graceful-shutdown-handler-guarded`.

**`cfg_set` mysteriously rewrote password in wrong section (commit `7babea2`, marathon 2026-06-02→07)** : `scripts/setup_master_network.sh::cfg_set` used `sed -i "s|^${key}\s*=.*|...|"` SANS adresse section-scoped → un `cfg_set hotspot password X` écrasait aussi `[admin] password`, `[home_wifi] password`, `[deploy] password`. Symptôme opérateur : "le mot de passe admin Flask a changé tout seul". Fix : adresse `/^\[${section}\]/,/^\[/` avant le `s|…|` (idiome déjà éprouvé dans `pair-sealing.sh`). **Règle** : tout sed in-place sur `local.cfg` DOIT être section-scoped.

**firstboot.service never runs, no `Astromech-XXXX` AP (commit `b8d2838`, marathon 2026-06-02→07)** : symptôme = Pi boote propre mais aucun hotspot, pas de Flask, pas de servos. Diagnostic : `journalctl -b -1 -u astromech-firstboot.service` → cherche `Found ordering cycle on …`. Cause : commit `3065d6c` avait ajouté `After=cloud-final.service` au template, mais `cloud-final.service` est `After=multi-user.target` et firstboot est `WantedBy=multi-user.target` → cycle → systemd drop SILENCIEUX d'une edge → firstboot tombe de la transaction. Fix `b8d2838` : revert le `After=cloud-final.service`. La race cloud-init/firstboot est résolue côté Imager (voir entrée suivante). **Règle** : aucun `After=` ne doit créer un cycle avec un `WantedBy=multi-user.target`.

**Boot 2 wipes the AP that Boot 1 created (commits Imager `0be1fa7` + `f961378`, marathon 2026-06-02→07)** : cloud-init `runcmd` (cc_scripts_user) tourne à CHAQUE boot (uptime ~22s). Sur Boot 1 il racait firstboot (~24s) et wipait ses profils NM ; sur Boot 2+ il re-wipait l'AP final. Fix en 2 étapes côté Imager : (a) `0be1fa7` marker-guard contre re-run, (b) `f961378` passage `runcmd` → `bootcmd` (cc_bootcmd) qui tourne en stage `cloud-init-local` à uptime ~7s, AVANT que NetworkManager soit démarré, AVANT que firstboot puisse être schedulé → plus de race possible. Marker gardé en belt-and-suspenders. Voir `docs/FIRSTBOOT.md` §3.

**Slave's `~/.ssh/authorized_keys` is empty after fresh flash (commit `b6fffff`, marathon 2026-06-02→07)** : symptôme = Master→Slave SSH key auth fail systématique, pair-sealing impossible. Cause : `scripts/setup_slave.sh` N'installait PAS `astromech-firstboot.service` → la Golden Image slave DD'd depuis un legacy slave n'avait jamais ce service → `/boot/firmware/astromech_secrets/authorized_keys` (master_pub) n'était jamais appliqué à `~/.ssh/authorized_keys`. Fix `b6fffff` : `setup_slave.sh` Step 7 installe + enable le shared `firstboot.service.template`. **Confirmer** : sur slave, `systemctl status astromech-firstboot.service` doit exister (Golden Image ≥ `07-06-2026.img.gz` la contient).

**Pairing deadlocké : slave joint l'AP puis disparaît, master coincé sur le SSID bootstrap (fix `d91068e`, 2026-06-12)** : symptôme = `AP-STA-CONNECTED` puis `DISCONNECTED` ~11 s plus tard dans le journal master, pair-sealing qui boucle `Slave not reachable... Exit 2`, et `/var/log/astromech-pair-sealing.log` qui s'arrête net sur `Slave reachable`. Cause historique : le sealing tournait pendant le boot-firstboot du master, poussait le SSID final au slave puis se faisait TUER par le reboot programmé du firstboot avant de flipper son propre AP → slave orphelin sur le SSID final, master sur le bootstrap, et le retry exige un ping devenu impossible. Diagnostic décisif : monter la carte slave et comparer `system-connections/astromech-master-hotspot.nmconnection` (ssid + mtime) au SSID diffusé par le master. Fix permanent : gate `ConditionPathExists=!ASTROMECH_FIRSTBOOT_READY` sur les 3 units + marqueur `pair_push_intent` écrit avant le push avec roll-forward auto après 180 s. **Réparation manuelle** (images pré-fix) : `nmcli connection modify astromech-hotspot 802-11-wireless.ssid <SSID-final>` + `up` + sed section-scopé de `local.cfg [hotspot]` + `systemctl start astromech-pair-sealing.service` (le chemin idempotent écrit le marker). Détails : `bd memories pair-sealing-firstboot-reboot-race`.
